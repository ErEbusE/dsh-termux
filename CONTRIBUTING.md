# Contributing to dsh-termux

User-facing docs (install / update / uninstall) live in [README.md](README.md) ([中文](README.zh-CN.md)); every Android fix and the patch mechanics live in [PATCHES.md](PATCHES.md). This file covers the contributor workflow: the update internals, testing gates, CI and releases. If you work through AI agents, [AGENTS.md](AGENTS.md) is the authoritative protocol they must follow — this file only summarizes the human-relevant parts.

## Reporting problems

Open an [issue](https://github.com/ErEbusE/dsh-termux/issues) with: device model and Android version, Termux version (`termux-info`), which install option you used (A: release / B: clone), the release tag or `dsh --version` output, and the **full** output of the failing command.

## Update mechanism internals

Referenced from the README's [Updating](README.md#updating) section.

### `dsh update` is a wrapper shortcut, not an upstream feature

Upstream dsh has only `web` and `plugin` as top-level subcommands, so the Termux wrapper generated by `scripts/common.sh` safely owns `update` as the **first** argument and hands the rest of argv to the bundled `update-dsh.sh` (a missing updater fails with an explicit message). Every other invocation reaches dsh untouched. Legacy: runtimes from releases before 1.1.0 have no wrapper shortcut — run the bundled updater at `~/.local/opt/dsh-termux-runtime/scripts/update-dsh.sh`; from 1.1.0+ the shortcut keeps itself current on every update.

### Patch-set updates vs npm updates

`dsh update` moves the **dsh npm version**. The **patch set** (and the updater itself) evolves with project releases instead — new or changed patches ship inside new releases of this project, not via npm. So before touching npm, every update run compares your runtime's bundled `VERSION` with the latest GitHub release and, when behind, **refreshes the patch set automatically**: it downloads the lightweight patch-set asset (~40 KB: the updater's own scripts + patches + `VERSION`), replaces those inside the runtime, and re-runs the update with the fresh set. `dsh update --self -y` forces the same refresh explicitly.

The refresh then **continues into the normal dsh update flow** — that step is where the fresh patches actually get applied to the installed dsh. Only want the refresh? Answer `n` at the "Update dsh to ...?" prompt to stop there; if the refresh brought a genuinely changed patch set, the updater reminds you that the new patches are not applied until you run `dsh update` again.

Runtimes from releases before 1.2.1 have no `VERSION` to compare and no patch-set asset to fetch: updates proceed with the old patch set (with a notice), and gaining the self-update machinery requires reinstalling via the release one-liner (README [Option A](README.md#installation)).

Both install options end up self-contained: the runtime bundles the updater and patches, so `dsh update` keeps working even if the repo checkout (Option B) is later moved or deleted. The updater never restarts a running `dsh web` — start/restart it yourself, which keeps the updater side-effect free. If a new dsh version changed the patched files so the patches no longer apply, the updater fails loudly and stops; that means the patches need regenerating, see [PATCHES.md](PATCHES.md).

## Testing your changes

The repo's iron rule (AGENTS.md §0): **agent-run tests are necessary but never sufficient**. Anything that lands on a real device (install, update, patches, browser handoff) must be verified by a human on a real Termux device before merge or release; otherwise it is labeled "未实测" (untested).

- Automated layer: `bash .test-install/run.sh all` (= r1+r2+r4+r5+r6) is the delivery gate; daily iteration is `run.sh r1`; the six routes and what each asserts are documented in [.test-install/README.md](.test-install/README.md).
- Human layer: `bash .test-install/serve.sh` runs the gate, then serves a sandbox `dsh web` (port 3141) for an on-device checklist. Sandboxes must never touch the live `~/.local/opt/dsh-termux-runtime/`, `~/.local/bin/dsh`, `~/.bashrc` or `~/.dsh/`.
- Per-change-type gates are tabulated in AGENTS.md §5 (e.g. `update-dsh.sh` ⇒ r4+r5+r6; patches/`patch-lib.sh` ⇒ CI verify + patch-check + r4 + r5; `00-setup.sh` pipeline ⇒ r3).
- Merge trail: after the human confirms, append a `Tested-by:` line generated by `bash .test-install/tb.sh "<coverage>"` (AGENTS.md §6.3).

## CI

| Workflow | When it runs | What it does |
|---|---|---|
| `verify.yml` | every PR / push to main, no npm install, <1 min | `bash -n` + ShellCheck over all tracked `*.sh`, patch-registry integrity, wrapper/`$BROWSER` generator tests, `install.sh` delegation guard, updater help-sentinel contract, test-harness entry/route registration, doc links/anchors (`.github/scripts/check-doc-links.py`) |
| `patch-check.yml` | when `patches/`, `scripts/patch-lib.sh` or `NODE_VERSION` change; when a PR touches `VERSION`; manual dispatch | installs dsh from npm, applies the patch set, checks markers, regression guards, boot smoke (~16 min, mostly npm) |
| `release.yml` | automatically when a `VERSION` change lands on main; also manual | builds and publishes the stable release; exits early if neither `VERSION` nor the bundled dsh version changed, fails if the tag exists |
| `pre-release.yml` | manual only | builds from the upstream dsh **source tree** and publishes a prerelease (pre channel); never touches `releases/latest` or the patch-set asset, so `--self` stays stable-channel-only |

`main` branch protection requires only the `static` check; `patch-check`/`pre-release` deliberately have no cron (see AGENTS.md §4 for why).

## Releases and versioning

- The project version lives in `VERSION` (X.Y.Z); release tags are `dsh-<bundled dsh version>-<VERSION>`.
- A release publishes automatically when a version change is pushed to main; separately, when only upstream dsh moved, the author manually triggers a release so fresh Option A installs get the newest dsh.
- A `VERSION` bump must be its **own single-file commit**, riding on the PR/branch that triggered it (AGENTS.md §6.6).
- After each release, re-pin the test baseline: `bash .test-install/run.sh baseline set <tag|latest>` — never hand-edit `baseline.env`.

## Working conventions

- Commit messages: English, conventional prefixes (feat / fix / refactor / docs / ci / housekeeping).
- Cross-file doc sweeps go through a branch + PR; only tiny post-merge fixes push directly (AGENTS.md §6.4).
- Adding a new Android adaptation: one section **plus** one Fix-index row in [PATCHES.md](PATCHES.md), a registry entry in `DSH_PATCH_SET` (`scripts/patch-lib.sh`), and a `VERSION` bump so a release ships it — the READMEs no longer carry a fixes table, so they need no edit unless user-facing behavior changed.
- When you change the updater's help text, keep the `# help-begin`/`# help-end` sentinel contract (CI asserts it); `README.md`/`README.zh-CN.md` parameter tables must match the sentinel.
- GitHub token for manual release/API work: `~/.config/dsh-termux/.env` (`GH_TOKEN`), sourced manually, never committed (AGENTS.md §2).
