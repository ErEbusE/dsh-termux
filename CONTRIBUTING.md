# Contributing to dsh-termux

User-facing docs (install / update / uninstall) live in [README.md](README.md) ([中文](README.zh-CN.md)); every Android fix and the patch mechanics live in [PATCHES.md](PATCHES.md). This file covers the contributor workflow: the update internals, testing gates, CI and releases. If you work through AI agents, [AGENTS.md](AGENTS.md) is the authoritative protocol they must follow — this file only summarizes the human-relevant parts.

## Reporting problems

Open an [issue](https://github.com/ErEbusE/dsh-termux/issues) with: device model and Android version, Termux version (`termux-info`), which install option you used (A: release / B: clone), the release tag or `dsh --version` output, and the **full** output of the failing command.

## Update mechanism internals

Referenced from the README's [Updating](README.md#updating) section.

### `dsh update` is a wrapper shortcut, not an upstream feature

Upstream dsh has only `web` and `plugin` as top-level subcommands, so the Termux wrapper generated by `scripts/common.sh` safely owns `update` as the **first** argument and hands the rest of argv to the bundled `update-dsh.sh` (a missing updater fails with an explicit message). Every other invocation reaches dsh untouched. Legacy: runtimes from releases before 1.1.0 have no wrapper shortcut — run the bundled updater at `~/.local/opt/dsh-termux-runtime/scripts/update-dsh.sh`; from 1.1.0+ the shortcut keeps itself current on every update.

### Patch-set updates vs npm updates

`dsh update` moves the **dsh npm version**. The **patch set** (and the updater itself) evolves with project releases instead — new or changed patches ship inside new releases of this project, not via npm. Two paths keep them in sync:

- **Automatic (plain `dsh update`)** — before touching npm, every run compares your runtime's bundled `VERSION` with the latest GitHub release and, when behind, refreshes the machinery: it downloads the lightweight patch-set asset (~40 KB: the updater's own scripts + patches + `VERSION`), replaces those inside the runtime, and re-runs the update with the fresh set. The refresh continues into the normal npm flow, where the fresh patches are applied to the newly installed dsh.
- **`dsh update --self` (patches only)** — refreshes the same machinery and then **applies the refreshed patch set to the installed dsh directly**, with no npm download or install. Because there is no reinstall to restore pristine files, the updater first reverses the previously applied set with its own bytes, then applies the new one. When the machinery content is already current it reports that and stops (`--force` re-applies anyway). `--patch-set <dir|tar.gz>` takes the set from a local source instead of GitHub — offline, for development and testing; build one with `build/build-patchset.sh`, which produces exactly the release asset layout. `--self` ignores `-t`/`-v` (it never moves the dsh version); use plain `dsh update` for that.

Runtimes from releases before 1.2.1 have no `VERSION` to compare and no patch-set asset to fetch: updates proceed with the old patch set (with a notice), and gaining the self-update machinery requires reinstalling via the release one-liner (README [Option A](README.md#installation)).

Both install options end up self-contained: the runtime bundles the updater and patches, so `dsh update` keeps working even if the repo checkout (Option B) is later moved or deleted. The updater never restarts a running `dsh web` — start/restart it yourself, which keeps the updater side-effect free. If a new dsh version changed the patched files so the patches no longer apply, the updater fails loudly and stops; that means the patches need regenerating, see [PATCHES.md](PATCHES.md).

## Testing your changes

The repo's iron rule (AGENTS.md §0): **agent-run tests are necessary but never sufficient**. Anything that lands on a real device (install, update, patches, browser handoff) must be verified by a human on a real Termux device before merge or release; otherwise it is labeled "未实测" (untested).

- Automated layer: `bash .test-install/run.sh verify` is the delivery decision — it computes the required cases from the change, and it is the only command that grants delivery qualification (`check` is a quick set, `full` is diagnostic); the case matrix is the single source of truth in `.test-install/cases/registry.tsv` (`run.sh list`), documented in [.test-install/README.md](.test-install/README.md).
- Human layer: `run.sh verify` opens a round and leaves a **frozen object** for every case that has a human item; `bash .test-install/serve.sh --round <round-id>` serves exactly that asserted tree (port 3141) for the on-device checklist, and `run.sh finalize <round-id> --observed <object-id>` closes the round. Sandboxes must never touch the live `~/.local/opt/dsh-termux-runtime/`, `~/.local/bin/dsh`, `~/.bashrc` or `~/.dsh/`.
- Which cases a change makes mandatory is **derived, not hand-listed**: `run.sh verify` computes them from the `changes` globs in `.test-install/cases/registry.tsv`. The human-only remainder (what CI and the sandbox cannot cover) is tabulated in AGENTS.md §5.
- Merge trail: after the human confirms, append a `Tested-by:` line generated by `bash .test-install/tools/tb.sh "<coverage>"`, or let `bash .test-install/tools/pr-merge.sh <PR> "<coverage>"` do the merge and write it into the merge commit (AGENTS.md §6.3).

## CI

| Workflow | When it runs | What it does |
|---|---|---|
| `verify.yml` | every PR / push to main, no npm install, <1 min | `bash -n` + ShellCheck over all tracked `*.sh`, patch-registry integrity, wrapper/`$BROWSER` generator tests, `install.sh` delegation guard, updater help-sentinel contract, test-harness entry point + case-registry integrity, the seven harness self-tests, doc links/anchors (`.github/scripts/check-doc-links.py`) |
| `patch-check.yml` | when `patches/`, `scripts/patch-lib.sh` or `NODE_VERSION` change; when a PR touches `VERSION`; manual dispatch | installs dsh from npm, applies the patch set, checks markers, regression guards, boot smoke (~16 min, mostly npm) |
| `release.yml` | automatically when a `VERSION` change lands on main; also manual | builds and publishes the release; a push exits early unless `VERSION` changed (a manual dispatch always proceeds), fails if the tag exists |
| `pre-release.yml` | manual only | builds from the upstream dsh **source tree** and publishes a prerelease (pre channel); never touches `releases/latest` or the patch-set asset, so `--self` stays stable-channel-only |
| `candidate-artifact.yml` | on PRs touching the packaging path, `VERSION` or `NODE_VERSION`; manual dispatch | builds from **npm** via `build/build-runtime.sh` and runs the same packaging phases `release.yml` does (shared `.github/scripts/package-runtime.sh`), then uploads the three-piece candidate as a workflow artifact. Publishes nothing and holds `contents: read` only. The **first** run must come from a PR event (that is how the workflow gets registered); after that, `gh workflow run candidate-artifact.yml --ref <branch>` also works on an **unmerged** branch — verified, so "you cannot dispatch before merge" is wrong. A device then fetches the artifact by exact run id (`bash .test-install/tools/fetch-candidate.sh <run-id>`) and runs `dry-run/candidate-artifact` and `release-install/candidate-artifact` against it (`DSH_CANDIDATE_ARTIFACT=<dir>`) |

`main` branch protection requires only the `static` check; `patch-check`/`pre-release` deliberately have no cron (see AGENTS.md §4 for why). `candidate-artifact.yml` is path-filtered too, so it must not be made a required check.

## Releases and versioning

- The project version lives in `VERSION` (X.Y.Z); release tags are `dsh-<bundled dsh version>-<VERSION>`.
- A release publishes automatically when a version change is pushed to main; separately, when only upstream dsh moved, the author manually triggers a release so fresh Option A installs get the newest dsh.
- The dsh spec a release bundles defaults to the `DSH_RELEASE_SPEC` repository variable when set, else `@deepseek-ai/dsh@latest`; a manual dispatch's `dsh_version` input overrides both. Pin it before a push-triggered release that must bundle a specific version: `gh variable set DSH_RELEASE_SPEC --body '@deepseek-ai/dsh@0.1.5-alpha.1'`.
- A `VERSION` bump must be its **own single-file commit**, riding on the PR/branch that triggered it (AGENTS.md §6.6).
- Seeds (`seeds/<name>.env`) are the test baseline; add or re-pin one with `bash .test-install/run.sh seed set <tag|latest> [<name>]`, and never hand-edit the file. Old seeds are kept on purpose (ADR-004), and a seed change goes through PR review like any other change — the old "re-pin after every release, push straight to main" rule is gone.

## Working conventions

- Commit messages: English, conventional prefixes (feat / fix / refactor / docs / ci / housekeeping).
- Cross-file doc sweeps go through a branch + PR; only tiny post-merge fixes push directly (AGENTS.md §6.4).
- Adding a new Android adaptation: one section **plus** one Fix-index row in [PATCHES.md](PATCHES.md), a registry entry in `DSH_PATCH_SET` (`scripts/patch-lib.sh`), and a `VERSION` bump so a release ships it — the READMEs no longer carry a fixes table, so they need no edit unless user-facing behavior changed.
- When you change the updater's help text, keep the `# help-begin`/`# help-end` sentinel contract (CI asserts it); `README.md`/`README.zh-CN.md` parameter tables must match the sentinel.
- GitHub token for manual release/API work: `~/.config/dsh-termux/.env` (`GH_TOKEN`), sourced manually, never committed (AGENTS.md §2). Maintainer GitHub operations use the [`gh` CLI](https://cli.github.com/) — installing it is recommended; `gh` reads `GH_TOKEN` from the environment, so sourcing that file is the only authentication step. Device-side scripts deliberately never depend on `gh`.
